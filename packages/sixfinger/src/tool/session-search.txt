You have the `session_search` tool: a full-text search over the persistent session history stored in the SQLite database.

## Why this exists

Long sessions get compacted: the model context window holds only a summary plus the most recent turns. Compaction NEVER deletes anything from the database — every message, tool output, and decision ever made in this session (and past sessions) stays in SQLite forever. This tool is your window into that complete history.

## When you MUST use it

- **After compaction**: you noticed you are missing details you believe were established earlier (a function name, a decision, a constraint, an error message). Do not guess — search.
- **Complex multi-step tasks**: before claiming something was "never discussed" or "does not exist", search the history first.
- **User references the past**: phrases like "the thing I mentioned earlier", "that API key from before", "as we discussed", "the error we saw yesterday" — search instead of asking the user to repeat themselves.
- **Cross-session recall**: with `scope: "all"` you can find things from previous sessions ("what did we decide about the cache invalidation last week?").
- **Verifying claims**: before telling the user "this was already implemented", verify against the actual historical messages.

## How to use it

- Start with plain text queries (`is_regex: false`, the default): a function name, a file path, an error string, a config key. Queries are case-insensitive.
- Switch to regex (`is_regex: true`) for structural patterns:
  - `apiKey\s*[:=]\s*['"][^'"]+` — find API key assignments
  - `(error|failed|exception).{0,40}cache` — error mentions near a topic
  - `https?://[^\s"'<]+` — URLs that were shared
  - `TODO|FIXME|HACK` — leftover markers discussed
  - `(decided|agreed|chose) .{0,60}(postgres|sqlite|redis)` — decisions about a technology
- `scope: "all"` searches every session in the database; use it when the detail might predate this session. `scope: "current"` is faster and scoped to this conversation.
- Filter with `role: "user"` to find what the user asked/decided, `role: "assistant"` for what was implemented/reported.
- Raise `limit` if the first results look truncated; lower it when there are too many generic matches.

## Zooming in

Results are snippets (150 characters around each match by default). When a snippet is promising but not enough:

- **Read the whole message**: re-run with `message_id` set to the result's `message_id`. This dumps every part of that message in full — surrounding text, tool outputs, attachments — so you can judge it in context. This is the preferred way to see "what was around" a match.
- **Widen the snippet**: pass `context` (up to 2000 characters) to see more around each match without dumping full messages.

Typical flow: search `ICEBERG` → the snippet hints at a decision but cuts off → re-run with `message_id` from that result → read the full exchange.

## Reading the results

Each result gives you the role, timestamp, a context snippet around the match, the message ID, and the session ID. Results include the ORIGINAL text of compacted parts — the `[compacted]` placeholders you see in context are just window dressing; the real content is here. When a result matters, zoom in with `message_id` or Read referenced files from the snippet.

Rules of thumb:
- Prefer two or three targeted searches over one broad one; refine the pattern when the first pass returns noise.
- If a regex query errors, fix the pattern rather than giving up on search.
- Never fabricate historical details you cannot find. An honest "I searched and found nothing" beats an invented memory.
